Ask your own health data real questions.

Health MCP connects one Google Health account — the data a Fitbit tracker syncs every day — to an AI assistant through the Model Context Protocol. It runs on hardware I control — my laptop, or my own Google Cloud project — reads with my consent, and writes nothing.

How it works

Five hops, one owner

Every hop is the account owner's own account, own hardware, or own cloud project. No third party sits in the middle: the MCP process talks to Google directly, whether it runs on the owner's laptop or on Cloud Run in the owner's project.

01 · Owner-held

Tokens stay home

OAuth credentials and tokens live either in one owner-only directory on the owner's computer, or in Secret Manager and Firestore inside the owner's own Google Cloud project. The assistant can call tools; it can never see a token or the client secret.

02 · Read-only

Look, don't touch

Every granted scope ends in .readonly. The server can summarize a month of sleep; it cannot log, edit or delete a single data point in the Google Health account.

03 · Consent-scoped

Revocable in one click

Access exists only because the owner approved it on Google's consent screen, scope by scope. Removing the app in Google Account settings kills every stored token instantly.

Quickstart

Reproduce it yourself

The local path — three commands, after creating a Google Cloud OAuth client with the Google Health API enabled and http://127.0.0.1:3000/callback as the redirect URI. Requires Node.js 20+. To reach the same data from a phone instead, see Cloud Run.

terminal
# configure: client ID + secret, scopes, MCP client wiring
$ npx -y google-health-mcp-unofficial setup --client claude --scope-preset full

# authorize: opens Google's consent screen, saves tokens locally
$ npx -y google-health-mcp-unofficial auth

# verify: proves the Google Health API answers with your token
$ npx -y google-health-mcp-unofficial doctor --live

Under the hood. Health MCP is my personal deployment and configuration of the open-source google-health-mcp-unofficial connector (MIT) against the Google Health API — the successor to the retired Fitbit Web API. Credit for the connector goes to its authors.

Cloud Run

Same server, nothing left switched on

The local setup only answers while my laptop is awake. A second deployment runs the identical MCP server on Google Cloud Run, inside the same project that already holds the OAuth client and the health data — so a question asked from a phone, mid-run, gets an answer with no computer on anywhere.

04 · One boundary

My project, my bill

Cloud Run, Firestore, the OAuth client and the health data all sit in a single Google Cloud project I own — one console, one bill, one place to audit. Still no server belonging to anyone else in the path.

05 · Secret URL

The path is the password

There is no login on the endpoint: claude.ai speaks plain HTTPS and cannot sign Google IAM requests, so every route sits under a 256-bit random path segment. Whoever holds that URL can read the data, so it is treated as a credential and rotated by redeploying.

06 · Filtered

Identity and GPS stripped

Every API response passes through a filter that deletes name, email and location keys before the model sees them. Tokens live in Firestore, refresh themselves, and never appear in a response or a log line.

terminal
# deploy: Cloud Build reads the Dockerfile — no local Docker needed
$ cd cloudrun && gcloud run deploy health-mcp --source . --region us-central1 \
      --set-secrets=GH_CLIENT_ID=gh-client-id:latest,SECRET_PATH=health-mcp-secret-path:latest

# authorize once in any browser — tokens land in Firestore, then refresh themselves
$ open "https://$SERVICE_URL/$SECRET/authorize"

# then paste the /mcp URL into claude.ai as a custom connector
$ echo "https://$SERVICE_URL/$SECRET/mcp"
Status

One user, on purpose

This is a personal tool, not a service. The only account that can sign in is mine, and everything it runs on is mine — my laptop, or my own Google Cloud project. If it ever grows into something other people can use, it will go through Google's app verification first — until then, treat everything here as documentation of a working single-user setup.

Planned next: scheduled weekly summaries, longitudinal charts against training logs, and a small evaluation of how well assistant answers stay grounded in the retrieved numbers.
