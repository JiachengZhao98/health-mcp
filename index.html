How it works

Five hops, one owner

Every hop is the account owner's own account or own hardware. There is no server in the middle belonging to this project — the MCP process runs locally and talks to Google directly.

01 · Local-first

Tokens stay home

OAuth credentials and tokens live in one directory on the owner's computer with owner-only file permissions. The assistant can call tools; it can never see a token or the client secret.

02 · Read-only

Look, don't touch

Every granted scope ends in .readonly. The server can summarize a month of sleep; it cannot log, edit or delete a single data point in the Google Health account.

03 · Consent-scoped

Revocable in one click

Access exists only because the owner approved it on Google's consent screen, scope by scope. Removing the app in Google Account settings kills every stored token instantly.

Quickstart

Reproduce it yourself

Three commands, after creating a Google Cloud OAuth client with the Google Health API enabled and http://127.0.0.1:3000/callback as the redirect URI. Requires Node.js 20+.

terminal
# configure: client ID + secret, scopes, MCP client wiring
$ npx -y google-health-mcp-unofficial setup --client claude --scope-preset full

# authorize: opens Google's consent screen, saves tokens locally
$ npx -y google-health-mcp-unofficial auth

# verify: proves the Google Health API answers with your token
$ npx -y google-health-mcp-unofficial doctor --live

Under the hood. Health MCP is my personal deployment and configuration of the open-source google-health-mcp-unofficial connector (MIT) against the Google Health API — the successor to the retired Fitbit Web API. Credit for the connector goes to its authors; the deployment choices, this site, and the privacy stance are mine.

Status

One user, on purpose

This is a personal tool, not a service. The only account that can sign in is mine, and the only computer it runs on is mine. If it ever grows into something other people can use, it will go through Google's app verification first — until then, treat everything here as documentation of a working single-user setup.

Planned next: scheduled weekly summaries, longitudinal charts against training logs, and a small evaluation of how well assistant answers stay grounded in the retrieved numbers.
